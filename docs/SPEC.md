## 0. Видение продукта

JobAgent — персональный AI-агент, который каждый день находит самые свежие релевантные вакансии на hh.ru/hh.kz, оценивает их по профилю пользователя, пишет персонализированные сопроводительные письма и отправляет отклики — в автопилоте или через одно нажатие «одобрить» в Telegram.

**Двойная цель (обе обязательны):**
1. **Практическая:** реально экономить время владельца и повышать конверсию откликов в интервью.
2. **Витринная:** быть демонстрабельным портфолио-проектом уровня «вау» — с публичной демо-версией, живыми метриками и красивым кейсом.

**Ключевой дифференциатор против существующих автокликеров (AI Hawk и пр.):** качество вместо спама — двухступенчатый скоринг, порог важнее лимита, guardrails вокруг LLM-действий, письма только из проверенной базы фактов.

---

## 1. Принципы (non-negotiable)

1. **Порог важнее лимита.** Если выше порога релевантности 3 вакансии — отправляем 3, а не добираем мусор до дневного лимита.
2. **Ноль выдумок.** Письмо может использовать только факты из базы знаний профиля. Никаких придуманных метрик, работодателей, навыков.
3. **Человек может ветировать любое действие.** Режимы: review (всё вручную), veto (автоотправка через таймаут), autopilot (сразу).
4. **Никаких двойных откликов.** Синхронизация состояния с hh ежедневно.
5. **$0/мес инфраструктура** на старте (бесплатные тиры + BYOK для мульти-юзера).
6. **Всё логируется:** каждый прогон, каждое решение LLM, стоимость токенов — это данные для аналитики и будущего кейса.

---

## 2. Режимы продукта

- **v0 — личный (single-user):** один пользователь (владелец), без регистрации. Цель — польза уже на этой неделе.
- **v1 — публичная бета (multi-user):** онбординг новых пользователей, OAuth hh, BYOK (свой ключ LLM), изоляция данных.
- **Демо-режим (read-only):** публичная страница с засеянными реалистичными данными — любой посетитель портфолио может покликать интерфейс без аккаунта. Реальные личные данные в демо не попадают.

## 3. Функциональные требования

### 3.1 Онбординг-мастер (v1; в v0 — конфиг файлом)

Флоу «LLM извлекает → пользователь подтверждает в редактируемой форме»:

1. Пользователь загружает резюме (PDF/текст) → LLM через structured output предлагает черновик конфига: целевые роли, поисковые запросы, грейд, навыки, зарплатный минимум.
2. Мастер из 4 шагов со свободными ответами:
   - «Опиши идеальную вакансию своими словами»
   - «Куда точно не хочешь?» (компании, технологии, форматы)
   - «Формат работы и локации?»
   - «Сколько откликов в день максимум и какой режим отправки?»
3. LLM извлекает ответы в структуру → экран подтверждения: всё показано как редактируемые поля/слайдеры/чекбоксы → «Сохранить и запустить».

### 3.2 База знаний профиля

Источники фактов для писем (только они!):
- текст резюме (может быть несколько версий: «AI-инженер», «аналитик»);
- карточки проектов: название, ссылки (демо/GitHub/кейс), стек, 3–5 буллетов «что построено», честные метрики;
- GitHub: подтягивать список репозиториев + README (по username, публичный API GitHub);
- свободные заметки владельца («обо мне», ограничения, предпочтения).

Хранить как структурированный JSON + полнотекст для контекста LLM. Редактируется через UI (и конфиг-файлом в v0).

### 3.3 Источники вакансий и лесенка деградации hh (NEW v1.1)

Основной источник — официальный API hh.ru/hh.kz (см. раздел 6). Важно: **поиск вакансий (`GET /vacancies`) авторизации не требует** — только заголовок `HH-User-Agent`. OAuth нужен лишь для откликов (`POST /negotiations`) и `/resumes/mine`. Поэтому система не «API или костыль», а лесенка режимов с автоматическим определением возможностей при каждом прогоне.

**Health-check на старте прогона:**
1. `check_search()`: `GET /vacancies?per_page=1` → 200? `search_api_ok = true`. **NEW v1.2 — различать тип отказа:** 403 `{"type":"forbidden"}` = IP-фильтр hh (антибот режет датацентровые IP: GitHub Actions, Vercel, VPS); 5xx/timeout = временная недоступность. При IP-блокировке — повторить запрос с OAuth-токеном (авторизованные вызовы обычно пропускаются); помогло → работаем с токеном; не помогло → режим FALLBACK + алерт владельцу «перенеси поллер на жилой IP».
2. `check_oauth()`: `GET /resumes/mine` с токеном → 200? `oauth_ok = true`. При 401/403 — одна попытка refresh токена; неудача → `oauth_ok = false`.

**Хостинг поллера (NEW v1.2):** поллер живёт только в облаке (GitHub Actions) — локальная машина владельца не рассматривается (не включена круглосуточно). Порядок устойчивости к IP-фильтрации hh: (1) запросы с OAuth-токеном из GitHub Actions — проверить первым делом после одобрения; (2) при сохраняющейся 403 — проксирование только запросов к hh через жилой прокси (настройка `hh.proxy_url`); (3) крайний случай — FALLBACK на email-подписки: Gmail API доступен из любого датацентра, поэтому этот путь не зависит от IP-фильтрации hh вообще.

**Матрица режимов** (настройка `hh.mode`, дефолт `auto`; `full|no_oauth|fallback` — принудительно):

| Условия | Режим | Поведение |
|---|---|---|
| `search_api_ok && oauth_ok` | FULL | Всё по ТЗ: сбор → скоринг → письма → автоотправка |
| `search_api_ok && !oauth_ok` | NO_OAUTH | Сбор, скоринг, письма работают полностью. Вместо автоотправки — ручной ассистент (см. 3.6): карточка с [📋 Скопировать письмо] и [🔗 Открыть вакансию] |
| `!search_api_ok` | FALLBACK | Источники-костыли (ниже). Отправка всегда ручная |

- О каждом переключении режима — сообщение в Telegram + `runs.stats.mode`.
- Как только health-check проходит — автоматический возврат в FULL. Никаких ручных «переключателей обратно».

**Источники-костыли для FALLBACK (по приоритету):**
1. **Email-подписки hh (основной костыль):** пользователь один раз создаёт на hh сохранённые поиски с email-оповещениями на свой Gmail. Система читает почту (Gmail API, отдельный label `hh-alerts`), извлекает из дайджестов ссылки на вакансии → далее обычный пайплайн. Легально, без парсинга.
2. **Ручной импорт:** команда бота `/add <url_вакансии>` или веб-форма «вставить текст вакансии» — скоринг и письмо по тому, что есть.
3. **Парсинг HTML-страниц hh — non-goal:** нарушает условия hh, капчи, хрупко. Не реализовывать.

В FALLBACK-режиме детали вакансии (`GET /vacancies/{id}`) могут быть недоступны — скоринг и письмо строятся по полям из дайджеста (заголовок, работодатель, зарплата, фрагмент описания); в `evaluations.red_flags` писать «данные неполные: fallback-источник».

### 3.4 Ежедневный пайплайн (ядро)

Запуск по расписанию: **2 раза в день — 06:00 и 18:00 МСК** (03:00 и 15:00 UTC) — отклики ложатся в начало и конец рабочего дня рекрутера.

Шаги:
1. **Сбор:** для каждого поискового запроса из настроек — `GET /vacancies` с `order_by=publication_time`, пагинация до уже виденных вакансий. Период по умолчанию — последние 3 дня.
2. **Upsert** новых вакансий в БД (дедуп по hh id).
3. **Детали:** `GET /vacancies/{id}` только для новых — полное описание, key_skills, has_test, salary, published_at.
4. **Детерминированный префильтр** (без LLM, бесплатно): стоп-слова («только офис» при remote-настройке, senior-требования «5+ лет» при несоответствии грейда, стоп-компании, агентства-прокладки по признакам), несоответствие формата/локации. Исход записывается (`excluded`, причина).
5. **LLM-скоринг** выживших: оценка 0–10 + причины + риски + рекомендуемая версия резюме + зацепка для письма (промпт в разделе 7).
6. **Генерация писем** для вакансий со скором ≥ порога (по умолчанию 7).
7. **Отбор в дневной лимит** (алгоритм ниже).
8. **Отправка** по режиму (review/veto/autopilot).
9. **Синхронизация статусов:** `GET /negotiations` — обновить свои отклики (просмотрено/приглашение/отказ), пересчитать аналитику.
10. **Дайджест в Telegram:** что собрано, что отправлено, что ждёт решения, метрики дня.

### 3.4а. Дельта-поллинг свежих вакансий (NEW v1.2)

Цель: попадать в первые отклики на свежие вакансии, не дожидаясь большого прогона. Пуш-событий у hh API нет, поэтому — частый короткий опрос.

- **Расписание:** каждые 30 минут (в том же GitHub Actions workflow, что veto-sweep), только в окне 06:00–01:00 МСК (ночные часы рекрутера не работают — дельта копится к утреннему прогону).
- **Логика:** по каждому запросу `GET /vacancies?order_by=publication_time&period=1&per_page=20` → оставить только неизвестные id → префильтр → скоринг дельты (обычно 0–5 вакансий, стоимость копеечная).
- **Быстрый трек:** вакансии со скором ≥ `hot_threshold` (по умолчанию 8) и дневной лимит не выбран → письмо и отправка/карточка сразу, вне очереди. Скор 7–8 — в обычную очередь ближайшего большого прогона.
- **Квота общая на день:** дельта-отправки вычитаются из дневного лимита больших прогонов (лимит считается по всем отправкам за сутки).
- Настройки: `delta_poll.enabled`, `delta_poll.interval_min`, `hot_threshold`.

### 3.5 Алгоритм отбора в дневной лимит

```
Кандидаты = письмо готово И отклика ещё не было И скор ≥ порог
            И вакансия не старше 14 дней И has_test = false
Сортировка: скор DESC, published_at DESC   # свежие выигрывают при равном скоре
Отправляем: top-N, где N = дневной лимит (по умолчанию 10)
Если кандидатов < N — отправляем сколько есть (порог важнее лимита)
Остаток ждёт следующего прогона (не протухает до 14 дней)
```

### 3.6 Отправка откликов и режимы

- **review:** всё копится в очереди, отправка только по кнопке.
- **veto (рекомендуемый дефолт):** карточка в Telegram с кнопками [✅ Отправить] [✏️ Править] [⏭ Пропустить]; через таймаут (по умолчанию 60 мин) без реакции — отправляется автоматически.
- **autopilot:** отправка сразу, карточка приходит как уведомление post-factum.

Отправка: `POST /negotiations` (vacancy_id, resume_id выбранной версии, message=письмо). Ошибки (уже откликался, требуется тест, архив) — статус `failed` + причина в БД и дайджесте.

**Ручной ассистент откликов (режим NO_OAUTH, NEW v1.1).** Когда OAuth недоступен, автоотправка заменяется на «2 касания»: карточка в Telegram содержит [📋 Скопировать письмо] (бот присылает текст письма отдельным сообщением для удобного копирования) и [🔗 Открыть вакансию] (deep link `https://hh.ru/vacancy/{id}`). После ручного отклика пользователь жмёт [✅ Я откликнулся] — только тогда ставится статус `sent` с `manual=true`. Дневной лимит и отбор top-N работают и в этом режиме (очередь выдачи вместо очереди отправки). Статистика конверсии продолжает собираться — синк статусов в NO_OAUTH невозможен, поэтому пользователю раз в 3 дня приходит опрос: «По этим откликам есть движение?» с кнопками [👀 Просмотрели] [📞 Пригласили] [❌ Отказ] [🤐 Тишина].

## 6. hh API — справка для реализации

База: `https://api.hh.ru`. Обязательный заголовок: `HH-User-Agent: JobAgent/1.0 (email@example.com)`.

- **Поиск:** `GET /vacancies`
  - `text` — запрос; синтаксис: `"AI-инженер" OR "LLM"`, `!` для исключений
  - `area` — регион (113=Россия, 1=Москва, 40=Казахстан; уточнить через `GET /areas`)
  - `order_by=publication_time`, `period=3` (дней), `per_page=100`, `page=N`
  - фильтры: `schedule=remote`, `employment=project`, `experience=between1And3`, `only_with_salary=true`
- **Детали:** `GET /vacancies/{id}` → description (HTML — очистить в текст), key_skills, has_test, response_letter_required, published_at, archived.
- **Мои резюме:** `GET /resumes/mine` (OAuth) → список resume_id и их названий.
- **Отклик:** `POST /negotiations` `{vacancy_id, resume_id, message}` → 201. Ошибки 400/403: уже откликался, требуется тест, вакансия в архиве — обрабатывать и писать в `applications.error`.
- **Мои отклики:** `GET /negotiations` (OAuth) → синк статусов (viewed/invited/rejected).
- **OAuth:** `https://hh.ru/oauth/authorize?response_type=code&client_id=..&redirect_uri=..` → `POST /oauth/token`. Хранить access+refresh токены в Supabase (шифровать), обновлять по истечении.
- Rate limits: ≤5 запросов/сек, при 429 — экспоненциальный backoff.

## 7. Промпты

### 7.1 Скоринг (structured output)

```
Система: Ты — скоринговый движок рекрутера. Оцени соответствие вакансии профилю кандидата строго по фактам профиля. Не придумывай опыт. Выведи ТОЛЬКО JSON.

Вход: PROFILE_JSON (роли, навыки, проекты, ограничения) + VACANCY (title, employer, salary, description, key_skills, published_at).

JSON-выход:
{
  "score": 0-10,                       // 9-10 идеально, 7-8 сильное совпадение, 5-6 частичное, <5 нет
  "verdict": "strong|partial|no",
  "reasons": ["..."],                  // 2-3 совпадения с фактами профиля
  "red_flags": ["..."],                // пробелы кандидата под требования
  "resume_version": "ai_engineer|analyst",
  "letter_hook": "..."                 // главная зацепка для письма: чем профиль бьёт в задачи вакансии
}
Штрафы: требуемый стек, которого нет в профиле (-2), senior-грейд при middle-профиле (-3), onsite-only при remote-настройке (-10, отклонить).
```

### 7.2 Письмо

```
Система: Ты пишешь сопроводительное письмо от первого лица. ЖЁСТКИЕ ПРАВИЛА:
1) только факты из PROFILE_FACTS — запрещено выдумывать метрики, работодателей, навыки;
2) язык = язык вакансии; 3) длина ≤ 1800 знаков; 4) тон: уверенный, конкретный, без воды и клише;
5) структура: зацепка под ИХ задачу (из letter_hook) → 2-3 доказательства проектами с ссылками → честная строка про главный пробел, если red_flags критичны (с компенсацией) → CTA (созвон/тестовое);
6) не упоминать «вайбкодинг».

Вход: PROFILE_FACTS (JSON) + VACANCY (очищенное описание) + letter_hook + tone_settings.
Выход: только текст письма.
```

### 7.3 Онбординг-извлечение

```
Вход: текст резюме + ответы мастера (4 свободных ответа).
JSON-выход: { roles[], search_queries[] (синтаксис hh), grade, salary_min, currency,
formats[], locations[], stop_words[], stop_companies[], daily_cap, send_mode, tone }
```

## 8. Guardrails

1. Вакансии старше 14 дней — никогда.
2. `has_test = true` — не отправлять, помечать «нужен ручной отклик».
3. Повторная отправка запрещена: проверка по `applications` + синк `GET /negotiations`.
4. Дневной лимит — жёсткий, per user.
5. Письмо отклоняется, если LLM использовала факт вне PROFILE_FACTS (валидация: ссылки и числа должны присутствовать в базе знаний).
6. Логирование стоимости: токены и $ на прогон; алерт, если дневная стоимость > порога.
7. Каждое автоматическое действие обратимо статусом (vetoed/failed с причиной).
8. NEW v1.1: health-check выполняется при каждом прогоне; режим прогона фиксируется в `runs.stats.mode`; смена режима — уведомление в Telegram.
9. NEW v1.1: в режимах NO_OAUTH/FALLBACK статус `sent` ставится только по явному подтверждению пользователя (кнопка «Я откликнулся») — система никогда не считает ручные действия выполненными автоматически.
10. NEW v1.2: антибот hh режет анонимные вызовы API с датацентровых IP (403). Любой запрос к hh должен уметь: (а) распознавать IP-блокировку по телу ответа, (б) повторять с OAuth-токеном, (в) при неудаче — уходить в FALLBACK с алертом, а не молча падать. Хост поллера конфигурируем: GitHub Actions или локальная машина владельца.

## 11. Roadmap

**v0 (2–3 вечера, single-user, польза сразу):** ✅ РЕАЛИЗОВАНО.
hh API сбор → дедуп → префильтр → скоринг → письма → Telegram-карточки с кнопками → режим veto → синк статусов → таблица в Supabase. Конфиг — файл. UI — минимальная очередь.

**v0.5 (NEW v1.1, 1 вечер):** лесенка деградации (раздел 3.3): health-check при каждом прогоне, режим NO_OAUTH с ручным ассистентом (кнопки копирования/deep link/«Я откликнулся», опрос статусов раз в 3 дня), настройка `hh.mode`. ## 12. Критерии готовности v0 (acceptance)

- [ ] Прогон проходит 5 дней подряд без ручного вмешательства.
- [ ] 0 двойных откликов, 0 отправок на вакансии старше 14 дней или с has_test.
- [ ] Каждое письмо содержит только факты из базы знаний (проверка выборки).
- [ ] Дайджест в Telegram приходит после каждого прогона.
- [ ] Стоимость ≤ $0.10/день.
- [ ] Режимы review/veto переключаются командой бота.
- [ ] NEW v1.1: при отключённом/неверном OAuth система работает в NO_OAUTH: сбор, скоринг, письма и выдача top-N в Telegram не прерываются.
- [ ] NEW v1.1: при недоступном поиске API система уходит в FALLBACK (email-подписки или ручной импорт) и сообщает режим в дайджесте.
- [ ] NEW v1.1: возврат в FULL происходит автоматически после успешного health-check, без ручных действий.
